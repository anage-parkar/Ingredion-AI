Cohort rollout and the RPA transition

  • Cut-over is a routing change, not a code change. Ingredion assigns a cohort of customers to the agent's Salesforce queue; from then on the agent is the primary processor for those customers and the Existing RPA no longer sees them. Moving a cohort back is the same change in reverse, which is also how the kill switch fails back.
  • Shadow first, per cohort. A cohort runs in shadow (the agent processes, the RPA still creates the orders, results are compared) before it is moved, so the agent's completion rate is known against the RPA's on the same customers.
  • The RPA stays deployable until Ingredion retires it (an Ingredion decision informed by the closure report). Parkar does not change it.
  • Volume. Primary processing for all cohorts is several times the failed-case volume the earlier, failure-only draft was sized for; reviewer capacity, Gemini quota and run cost per cohort are measured in shadow mode before each cut-over.

Measures: the SOW 2.7 scorecard

SOW No. 07 (section 2.7) sets six measures for Agent A: completion rate (share of email order cases completed as SAP sales orders), field-level accuracy, undetected errors, reviewer confirmation, handling time and run cost. Their thresholds are set at Gate 1 from the Stage 1 backtest of 500 past POs including RPA-failed POs, with the final SAP orders as the answer key, and they are the basis for Gates 4 and 5. The earlier targets in the clarification responses (recovery ≥ 50% at Gate 1, ≥ 70% at Gate 4, ≥ 80% before Phase 2; undetected errors ≤ 2% of key fields, ≤ 0.5% before Phase 2) were written for the failed-case scope and now serve only as Parkar's starting proposal; the headline measure we propose is the completion rate on a cohort against the Existing RPA's automation rate on the same cohort. From Stage 5 Parkar reports twelve measures from the audit trail and dashboards (cases received and completed, orders created, incompletion items and follow-ups, reviewer corrections, cases returned to the rework path, failure reasons by category, accuracy and undetected errors, handling time, run cost, trends against the baseline).

Production modes

  • Shadow (per cohort): live cases, no SAP order, no Salesforce update, no Outlook draft; results compared with the RPA's or the manual order; tuning.
  • Assisted (Phase 1): every result confirmed or corrected by an Ingredion reviewer before A8; corrections feed the evaluation set.
  • Phase 2 (Gate 5 decision): high-confidence cases skip the gate; anything with a price, contract or availability discrepancy, a rule failure, a revised or duplicate submission, or a possible SAP duplicate always goes to the reviewer.

Decisions the redline leaves for the stages

  • Google Cloud services and the review queue app design [Stage 2]; the SAP method, order API or BAPI, through APIM [Gate 2].
  • Validation location, SAP or Google Cloud [recommended Stage 1, decided Gate 1].
  • Read interface or scheduled extract per source; SAP pricing, contract and ATP reads [Stage 1].
  • Cohort order and shadow duration per cohort; reviewer capacity per cohort [Gate 1].
  • Phase 2 criteria for skipping the gate [Gate 5].

Agent BPre-bill Validation and Dispute Prevention Agent on Google Cloud

Unchanged in its eight steps since 16 October and moved to the Ingredion Google Cloud project by redline v2, with all four checks in the first release. The verdict on the whiteboard sketch, the refined flow and the rules are kept below; what redline v2 changes for this agent follows at the end of the section.

Feasible

The skeleton in the sketch is the SOW's own design: pull PO and invoice into one schema, let rules decide, invoke a Gemini agent only afterwards to write the reasoning, and notify people through a review queue app. Six things change between the sketch and what we will build:

  1. Code owns the verdict, the model owns the explanation. The box labelled "Draft Reasoning Verdict" splits in two: B5 (rules) produces the outcome; B6 (Vertex AI) only explains it and drafts the request. The model can never change an outcome.
  2. One verdict becomes three outcomes. Matched · Updated PO required · Fix our side or decide. A matched invoice is recorded and never waits for a person or a model call.
  3. "Ingredion Platform" is six named read-only sources, reached through one dedicated identity that can read and never write: SAP, PROS, Salesforce, Ariba, TermSync, contract and fuel-rate files.
  4. The email → Graph API → PDF path is a fallback, not the main road. B3 reads structured PO data first; a PDF is parsed only when no structured PO exists, and its text is screened by Model Armor before any model sees it.
  5. The review queue app records the decision, not just an email. The named owner confirms or overrides every flagged case (B7); nothing skips this step.
  6. Four pieces the sketch did not have: the B1 trigger from SAP, missing-data handling in B2, the append-only audit trail (B8) with the recheck loop when the updated PO arrives, and the evaluation scorecard that gates every release.

The five rules

CheckRuleRelease
Unit priceExact after UOM and currency conversion; SAP price at billing date versus PO price1
FreightAny charge not on the PO is flagged1
Fuel surchargeAny charge not on the PO is flagged, even if the contract allows it1
QuantityShipped quantity inside the PO range after UOM conversion; no tolerance stated means exact; over-shipments checked first2
Payment termsExact match; a backstop while the root fix lands at contract and order setup2

Anchor case for the test set: Kraft Heinz sales order 809-6862, which fails all five (40.14 vs 47.00 USD/CWT; a 300 USD surcharge not on the PO; 170,250 lb shipped against 170,000; 110 against 120 days). Clean, single-error, multi-error, missing-data and borderline orders sit beside it so the rules are not tuned to one order.

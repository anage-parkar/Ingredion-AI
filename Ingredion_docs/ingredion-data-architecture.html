Ingredion Data Architecture

How the two agents of the Ingredion Agentic AI Factory sit on the Ingredion Google Cloud data platform: SAP and Salesforce data replicated by Acersoft into a landing zone and refined through bronze, silver and gold layers; the agents read from gold and write back through an outbound path. Drawn from the data team's input of 26 October 2026 and SOW No. 07 (Ingredion redline v2, 20 October 2026).

Input of 26 Oct

The data team runs a medallion platform in the Ingredion Google Cloud environment. What this changes for the agents, and how firm each point is:

  1. Reads move to the platform. SAP and Salesforce data arrives in a Cloud Storage landing zone through Acersoft in near real time and is refined to gold. Agent A validates against the gold copy of SAP master data and discovers cases from the gold copy of Salesforce. Agent B assembles its evidence from the same place. Confirmed direction; it is also the answer to the SOW's "validation location" question at Gate 1 (A-D3, B-D3).
  2. Writes go back through an outbound path. The data team describes the same architecture for pushing data to SAP and for updating Salesforce. For Agent A that path carries the A9 order request and the A10 case update. To be confirmed: who runs the outbound leg, its latency, and how SAP's result (order number, errors, incompletion log) comes back. The SOW baseline is a direct SAP call through API Management; both options are drawn in figure 3 and the agent's state machine handles either.
  3. Agent B writes nothing to any Ingredion system, so it has no outbound leg at all. Its outputs stay in the agent's own stores plus an outcome dataset for reporting.
  4. The agents read gold, never bronze. Bronze is the data team's raw history; it has duplicates, late-arriving changes and the full breadth of SAP and Salesforce data. Gold is the interface, with a schema, a refresh time and an owner.
  5. Nothing from the platform goes to Gemini. The model sees the email, the PO and the agent's own summaries. Master data and order data are used by ordinary code in A4, A5 and B2 to B5.
  6. Three things still need a live call regardless of the platform: the incompletion log right after an order is created, availability (ATP is a calculation, not a table), and PO attachments unless the pipeline replicates files.

The write path: A9 and A10

The SOW baseline is a direct call through API Management. The data team describes an outbound path through the platform. The agent is built so that either works; what differs is latency and where the result comes from.

write live read platform dataset owned by Ingredion (data team or integration team)

What option 2 must guarantee

  • At-least-once with idempotency. The integration may retry; SAP must create one order per idempotency key (case id, PO number, revision). If SAP cannot enforce that, the integration keeps a key table and the agent's lookup is the last line of defence.
  • A result for every request. Every request row ends as succeeded or failed with SAP's messages, within an agreed time. Silence is "unknown" and triggers the lookup, never a retry.
  • Latency the reviewer can live with. Approval to order number in minutes, with p95 agreed. Longer than that and the reviewer loses the loop; the SOW's Phase 1 is built on a person seeing the result.
  • The incompletion log. Either the acknowledgement carries it, or the agent still needs one live SAP read after creation. Without it the case cannot be completed truthfully.
  • Dead letters and replay. A failed post is visible to both teams, replayable with the same key, and never silently dropped.

Recommendation to record at Gate 1

  • Reads from gold for both agents: decided, subject to the latency numbers.
  • A9 through API Management if the SAP API is available in Dev by Stage 3; the result is immediate and the incompletion log is on the same path.
  • Option 2 is acceptable when the guarantees on the left hold and p95 is within the agreed minutes. The connector changes, the steps do not.
  • A10 can use option 2 without much cost: the case update is not time-critical and carries the same key.
  • Whichever is chosen is written into the target architecture (A-D3), the integration specification (A-D10) and the environment design (A-D11), and the SOW wording for A9 is aligned through change control if the outbound path replaces API Management.

Decisions, risks and open questions

Decisions to record

  1. Validation location: Google Cloud, from gold. Target architecture A-D3 and B-D3 at Gate 1 (20 November 2026).
  2. A9 write path: API Management (baseline) or the outbound path (option 2), decided from the Dev evidence in Stage 2; integration specification A-D10 by 4 December 2026.
  3. Attachments: replicated files bucket or Salesforce API; needed before the prototype reads real cases in week 1.
  4. Availability: checked live before the gate, or left to SAP at creation with the result shown to the reviewer.
  5. Duplicate window: the lag of the sales-order table defines how long the agent's own record must cover.
  6. Agent B's four non-SAP sources: through Acersoft or a separate landing drop; owner and cadence per source.

Risks for the RAID log (SOW 8.2(c))

  • The ingestion pipeline is an Ingredion dependency: its outage stops validation. Mitigation: the staleness guard routes to review; the kill switch stops intake; no silent decisions on old data.
  • Latency not yet measured: if gold lags more than the agreed minutes, the duplicate check and B1 pick-up degrade. Mitigation: measure in Dev in week 1, agree the SLO at Gate 1.
  • Schema drift in gold breaks connectors. Mitigation: versioned schemas and contract tests in the build pipeline.
  • Test data parity: a Test platform with a different shape from Prod invalidates SIT. Mitigation: same schema in every environment, masked data in Test.
  • Option 2 latency or missing acknowledgements leave orders in "unknown". Mitigation: lookup-before-retry, dead-letter visibility, p95 in the contract.

Questions for the data team this week

  1. Project and dataset names per environment; which gold tables already exist for cases, customers, materials, CMIR, conditions, contracts and orders.
  2. How Acersoft captures changes per source (log-based change capture, triggers, scheduled extracts) and the measured latency from source change to gold today.
  3. Whether Salesforce and Ariba files (PO PDFs, scans, Excel, Word) are replicated, and where.
  4. How updates and deletes are represented in silver and gold, and whether effective-dated history is kept for conditions, agreements and terms.
  5. The outbound path: which tool posts to SAP and Salesforce, the interface used (BAPI, IDoc, OData, REST), how it acknowledges, and whether it can return the incompletion log.
  6. Idempotency: can SAP or the integration reject a second order for the same key.
  7. Notifications: Pub/Sub topics on gold refresh or on specific transitions, or do consumers poll.
  8. Who owns the gold schema, how changes are announced, and the escalation contact when a refresh fails.
  9. Access process and lead time for the two service accounts in Dev, so the Stage 1 clock is not held by IAM.
  10. Whether PROS, Ariba, TermSync and the contract and fuel-rate files are already on the platform or need onboarding for Agent B, and by when.

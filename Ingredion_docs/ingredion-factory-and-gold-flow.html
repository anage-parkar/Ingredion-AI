The factory package, and how the agents read gold data

Two questions from the Parkar engineering team, answered against the code as it stands on 30 October 2026: what kind of thing factory/ is (governance, LLM and agent operations, or something else), and exactly how a running agent gets its data out of the BigQuery gold tables and the Cloud Storage files bucket: what goes in, what comes back, and where it ends up.

Part 1What factory/ is

Answer

It is the factory's control plane and shared runtime, and it carries three concerns at once: governance, agent operations and execution mechanics. Calling it "the governance layer" is true of about half of it (the guardrails, the closed reason codes, the human gate, the append-only audit, the claims and state machines, the kill switch, the evidence); calling it "LLM / Agent Ops" is true of another third (the model gateway with versioned prompts, the evaluation scorecards, tracing, the outcome rows, one environment contract); the rest is plain runtime (the case, the poller, the dispatch between api and worker, the gold and file readers). The useful mental model is three layers in one package, with one rule that matters more than the name: factory imports neither agent, both agents import factory, and app imports all three.

  • Governance answers "what are the agents allowed to do, and can we prove afterwards what they did?"
  • Agent Ops answers "how do we run, measure, change and switch off the agents without touching their business logic?"
  • Runtime answers "how does a case physically move, and how does it reach the data?"

What is deliberately not in it

  • Business logic. A step that decides something about an order or an invoice lives in order_intake_agent/steps or prebill_agent/steps. The factory never knows what a PO is.
  • Connectors to Ingredion systems. The protocols, the gold readers, the landing readers and the stubs live with the agent that owns the read or write scope; the factory only supplies the generic gold and file clients they build on.
  • The HTTP surface and the worker loop. Those are app/, which imports everything; the factory offers routers as functions and never imports app.
  • Infrastructure. Buckets, topics, subscriptions with their dead-letter topics, service accounts and the Model Armor template are Terraform and Ingredion's, not Python.

How to say it to Ingredion. "The factory is the shared runtime and control plane of both agents. Its governance controls are the guardrails, the closed reason codes, the human gate, the append-only audit, one-case-once, the kill switch and the evidence bucket. Its operations capabilities are the model gateway, the scorecards, tracing, the outcome tables and one environment contract. The use-case logic sits above it and cannot bypass it, because every model call, every write and every decision passes through a factory component."

One cheap enforcement is worth adding in Stage 1: an import-linter contract that forbids factory from importing app, order_intake_agent or prebill_agent, run in the same CI job as the SOW 5.4 scans.

Part 2How the code reads gold data from BigQuery and Cloud Storage

In one paragraph

A step never knows where its data comes from. It calls a method on a connector protocol (ctx.sap_master.find_partner(role, text), ctx.pros.contract_price(sold_to, material, on_date), ctx.salesforce.get_email(case_id)). In the project those methods are implemented by the gold connectors, which inherit GoldReader. A gold connector turns the call into a Lookup (table, equality and range filters, order, limit), the reader first asks the staleness guard whether the table was refreshed recently enough (one query on ops.freshness, cached for a minute), then the BigQueryGoldClient validates the lookup against the table registry, renders one parameterised SELECT, runs it and returns the rows as plain dicts. The connector maps the dicts to the Pydantic models the steps already use (PartnerMatch, CMIRMatch, PriceRecord, CanonicalDoc, EmailBundle …). When a row points at a file (a PO attachment, a PO PDF), the connector fetches the object from the files bucket by its gs:// URI and verifies the SHA-256 recorded on the row before the bytes become an Attachment. What the step receives is therefore identical whether the backend is BigQuery or the in-memory twin the tests use.

Two ways a case reaches the agent, and what the input looks like

Event push (normal path). The data platform publishes a change signal; the subscription pushes it to the api. The body is a Pub/Sub envelope whose message.data is base64 JSON:

POST /events/order-intake/cases          Authorization: Bearer <OIDC token>
{ "message": { "data": base64({
      "case_id": "5003000000AbCdE", "cohort": "cohort-1",
      "customer_name": "Kraft Heinz", "received_at": "2026-11-03T14:02:11Z",
      "gold_refresh_ts": "2026-11-03T14:02:40Z" }),
    "attributes": {}, "messageId": "1234567890", "publishTime": "…" },
  "subscription": "projects/ingredion-prod/subscriptions/gold-cases-changed-agent-a" }

app/routers/events.py decodes it, runtime.raw_from_event(payload) turns it into an IntakeCase and then a RawCase(source_ref=case_id, marker=gold_refresh_ts, payload=IntakeCase as JSON), the api claims case_id once and publishes a WorkItem to the agent's work topic. The worker pulls it and calls pipeline.process_raw(RawCase).

Sweep (catch-up path). POST /api/order-intake/ops/poll runs the factory Poller over the agent's intake source. On gold that source is GoldCaseQueue, whose fetch(after) is itself a gold read:

Lookup("gold_cases.email_order_case",
       where={"routed_to": "agent"},
       gt={"updated_at": <last marker>},
       order_by=("updated_at",), limit=200)

Every row becomes the same RawCase shape as the event path (marker = updated_at), the poller claims each case and hands it to the dispatcher. For Agent B the source is GoldSAPBilling over gold_billing.invoice_ready_order with ready_at as the marker. Nothing downstream can tell the two paths apart.

Which class answers which protocol in the project

The runtime of each agent (order_intake_agent/runtime.py, prebill_agent/runtime.py) reads INGREDION_PLATFORM. With gold it builds one BigQueryGoldClient and one GcsFileStore through factory/wiring.py and hands them to every connector; with stub (the default on a laptop) it builds the in-memory stubs. The writes stay on the stubs in both modes until Gate 2.

One read, step by step

Figure 2 follows a single Order Intake case from the change signal to the moment A4 holds a list of SAP partners, with the file fetch and the write-back shown on the same picture. The numbers match the steps under the figure.

data platform (data team) api and worker factory platform code what the step receives written back by the agent
  1. The push arrives and is authenticated.

    app/push_auth.require_push_auth takes the bearer token Pub/Sub attached, verifies it with Google's keys against PUBSUB_PUSH_AUDIENCE and checks the email claim equals PUBSUB_PUSH_SERVICE_ACCOUNT. Without an audience (a laptop) the service key stands in. An engaged kill switch answers 503 so Pub/Sub keeps the message and retries later.

  2. The event becomes a RawCase and the case is claimed.

    intake_from_event(payload) accepts either the gold change signal or a full IntakeCase document and validates it with Pydantic; raw_from_event wraps it as RawCase(source_ref=case_id, marker=gold_refresh_ts, payload=…). ctx.claims.claim(case_id, owner="order_intake:event") is an atomic insert; a second delivery of the same case gets False, the api records event.duplicate in the audit and answers 204 without running anything.

  3. The run is handed to the worker.

    WorkItem.from_raw(agent, raw) is serialised as JSON and published to WORK_TOPIC_ORDER_INTAKE. If publishing fails the claim is released and the answer is 503, so the event comes back. On a laptop the InlineDispatcher calls the pipeline inside the request instead.

  4. The worker pulls and guards the lease.

    Worker.handle acknowledges a redelivery whose case is already at or past the gate (the runtime's restartable_states decide), otherwise it starts a lease thread that calls modify_ack_deadline every 240 seconds and runs the pipeline. A failure before the gate is a nack and a re-run from A1; GoldStale is a nack with a pause.

  5. The pipeline creates the Case.

    OrderIntakePipeline.process(IntakeCase) builds Case(case_id, agent), stores the intake record under case.data["intake"], starts the state machine and runs A1 onwards. Every step receives (case, ctx) and nothing else.

  6. A step asks a question in its own vocabulary.

    A4 needs the SAP partners that match the sold-to text the model extracted: ctx.sap_master.find_partner("sold_to", ex.sold_to). The same line ran yesterday against the stub and will run tomorrow against the data team's real columns; the step is not edited for either.

  7. The connector expresses the question as a Lookup. 
    class GoldSAPMasterData(GoldReader):
    def find_partner(self, role, text):
        found = {}
        for column in ("name", "customer_id"):          # the partner's name or id appears inside the PO text
            for row in self.rows(CUSTOMER, where={"role": role}, within={column: text}):
                if row.get("blocked"):
                    continue
                found.setdefault(str(row["customer_id"]), PartnerMatch(role=role, id=str(row["customer_id"]), name=row.get("name") or ""))
        return list(found.values())

    A Lookup has five kinds of filter and nothing else: where (equality, IN for a list, IS NULL for None), within (the column's value occurs inside a text), between (inclusive bounds, either side open), gt (markers), plus order_by and limit. There is no way to pass SQL.

  8. The staleness guard runs first. 
    def guard(self, table):
    spec = GOLD.table(table)                               # UnknownTable if it is not a gold table the agents read
    cached = self._checked.get(table)
    if cached and self._clock() - cached[0] < self.check_every_seconds:   # 60 s
        return cached[1]
    fresh = self.client.freshness(table)                   # SELECT … FROM ops.freshness WHERE table_name = @p0
    self._checked[table] = (self._clock(), fresh)
    self.refresh_used[table] = fresh.refreshed_at          # kept for the evidence snapshot
    limit = self.max_age_minutes if self.max_age_minutes is not None else spec.max_age_minutes
    if limit:
        age = fresh.age_minutes(self._now())
        if age is None or age > limit:                     # unknown freshness fails closed
            raise GoldStale(table, fresh.refreshed_at, limit)
    return fresh
  9. The client validates and compiles.

    Lookup.validate() compares every column named in the lookup with the registry entry for the table and raises UnknownColumn on a miss. compile() then renders one statement: identifiers (project, dataset with its environment suffix, table, columns) come from the registry, every value becomes a named parameter whose BigQuery type is derived from the Python type (str → STRING, int → INT64, float → FLOAT64, bool → BOOL, date → DATE, datetime → TIMESTAMP, a list becomes ARRAY<…> with IN UNNEST).

  10. BigQuery answers.

    client.query(sql, job_config=QueryJobConfig(query_parameters=[…])).result() is iterated and each row becomes dict(row). The client is created lazily with bigquery.Client(project=GOLD_PROJECT) under the service's own service account, which has bigquery.dataViewer on the gold datasets and nothing on bronze or silver.

  11. Rows become the models the steps already use.

    The connector maps dict keys to the Pydantic model fields and applies the small amount of domain logic that the stub had (blocked partners are dropped, a CMIR key is retried upper-cased, a condition's rate and unit become the tuple A5 expects). The step stores the result exactly where it did before, here Validation.sold_to inside case.data["validation"].

  12. Files travel by pointer and are verified. 
    for att in self.rows(ATTACHMENTS, where={"case_id": case_id}, order_by=("received_at", "name")):
    content = fetch_verified(self.files, att["file_uri"], att.get("sha256"))   # GcsFileStore → download_as_bytes → sha256 compare
    attachments.append(Attachment(name=att["name"], content_type=att.get("content_type") or "application/octet-stream", content=content))

    A hash mismatch raises IntegrityError and the case fails before any model sees the file. The bytes live only in the running case and, if a step keeps them as evidence, in the agent's own bucket.

  13. Evidence is written as the case progresses.

    ctx.keep(case, step, name, content) stores an object under <case id>/<run id>/<step>/<name> in EVIDENCE_BUCKET_ORDER_INTAKE and appends the URI to case.data["evidence_uris"]. A3 keeps the layout text per attachment and the raw Gemini answer, A6 the draft answer, A8 the SAP payload, A9 the SAP result; B2 keeps the whole evidence snapshot per version with the gold refresh times. A failed write is logged and alerted, never fatal.

  14. One outcome row per finished case.

    At the three terminal points (returned, duplicate closed, case updated) ctx.record_outcome(case) builds the case_outcome row (outcome, reason codes, cohort, PO number, order number, reviewer, decision, confidence, model calls and tokens, evidence URIs, the gold refresh times used, duration) and streams it with insert_rows_json; a correction also writes field_corrections rows. Agent B writes one prebill_outcome row per version in B8.

The staleness guard

A gold table is a copy. The guard turns "how old may the copy be before we must not validate against it?" into one number per table, kept in the registry next to the columns. The check costs one small query per table per minute per process, and the answer is remembered on the reader so the evidence can say which refresh every decision was based on.

The in-memory twin and the contract tests

InMemoryGoldClient implements the same two methods as the BigQuery client, rows(Lookup) and freshness(table), over lists of dicts keyed by the registry's table names, and applies every filter kind in Python. Because the connectors only ever speak Lookup, the identical connector classes run in the tests, on a laptop and in the project. The tests that pin the contract:

  • tests/platform/test_gold_platform.py: the registry's shape, every filter kind on the in-memory client, the exact SQL and parameter types the BigQuery client renders for a representative lookup, the freshness query, the staleness guard's cache and fail-closed behaviour, files by hash.
  • tests/order_intake/test_oi_gold_readers.py: the Order Intake test world written as gold rows; the full pipeline through the gate to a created order on the gold connectors; a previous order in gold detected as a duplicate; the master-data lookups against the stub semantics; a stale table releasing the claim through the poller; a tampered attachment refused.
  • tests/prebill/test_prebill_gold_readers.py: the Kraft Heinz anchor as gold rows caught four of four with the same verdicts, owners and evidence; the invoice-ready table as an intake source; the PO PDF fallback from the files bucket; the rate files and dispute history from landing-bucket CSVs.
  • tests/platform/test_evidence_outcomes.py: what both pipelines leave in the evidence store and the outcome sink, including one row per pre-bill version and the rule that a broken bucket never fails a case.

When the data team's DDL arrives. Change the table's entry in factory/platform/schema.py (columns, keys, limit), run the suite: any connector that names a column that no longer exists fails at Lookup.validate() in the in-memory tests before a single query reaches BigQuery; fix the mapping in the connector; done. The steps do not change. A new table the agents need is added to the registry first, then to a connector, then to a contract test with a few rows.

Limits and open points

  • Two reads are not copies. Availability (ATP) and the order lookup immediately after a SAP timeout need the live SAP connector; the gold connector delegates to it and reports "not checked" without one. The live connector is part of the Gate 2 write-path decision.
  • The registry is a proposal. Twenty gold tables plus ops.freshness, named and typed from the 26 October input. Column names, the open-ended validity convention and the refresh cadence per table are the data team's to confirm; the contract tests make each change visible.
  • Validity windows assume DATE columns and 9999-12-31 open ends. The client sends date parameters as DATE; a NULL valid_to would exclude the row. If the data team keeps nulls, the window becomes (valid_to IS NULL OR valid_to ≥ @p) in compile().
  • Partner matching is a substring test. find_partner asks whether the customer's name or id occurs in the extracted text, which is what the stub did and what the Stage 1 backtest will measure. A search-name table or a fuzzy match is a Stage 1 finding if the backtest needs it.
  • Streaming inserts into the outcome tables are simple and immediate but carry BigQuery's streaming quotas; at the expected volumes they are far from a limit. Load jobs are the fallback.
  • Synchronous pull in the worker (a pull request every 30 seconds with up to four messages) suits the case volume and keeps the lease logic explicit; streaming pull is a drop-in change inside PubSubWorkQueue if latency ever matters.
  • The pre-bill case store is still in memory in the worker; a Mongo store like Agent A's is needed before a recheck can arrive in a different process than the first run.
